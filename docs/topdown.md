## Реализованный этап

Это техническая основа MAP01, а не завершённый сюжетный вертикальный срез.

`/rpg.html` использует самостоятельный `public/engine/rpg/tarikh-rpg.wasm` без JS-рендерера и без Doom. `/` остаётся Beta. Серверные данные, исходники Doom, старые карты и правила оценивания сохранены.

- `src/rpg/renderer.hpp`: RGBA framebuffer 480×320, альфа-композиция, палитровые спрайты.
- `world.hpp`: тайлы 16×16, трава, земля, река, мост, скалы, деревья, машина времени и лагерь. Два самостоятельных экрана, без прокрутки камеры.
- `engine.cpp`: фиксированный шаг 60 Гц, нормализованное движение, коллизии ног и границы, ходьба/idle, порядок отрисовки по глубине, fade-переходы и безопасные точки появления. C++ определяет близость объектов и события диалогов. Здоровье 100 и три жизни — начальные значения; боя пока нет.
- `main.js`: только загрузка WASM, ввод, планирование кадров, копирование framebuffer в Canvas и DOM-интерфейс. Потеря фокуса/видимости ставит игру на паузу. Масштабирование целочисленное; на узком телефоне доступна горизонтальная прокрутка карты, полноценная мобильная компоновка отложена.
- Графика выполнена в коде, без сторонних ресурсов; это предварительный пиксельный набор, а не финальный художественный пакет. Реплики художественные, исторические квизы не добавлены.

ABI: `tj_init`, `tj_input(mask)`, `tj_tick`, `tj_render`, `tj_pixels`, `tj_pause`, `tj_ack`, `tj_state(field)`, `tj_tile(zone,x,y)`. Ввод: вверх=1, вниз=2, влево=4, вправо=8, действие=16. `tj_state`: x/y в тысячных пикселя (0/1), зона (2), направление (3), шаг анимации (4), fade (5), событие (6), посещённые зоны (7), здоровье/жизни (8/9), ticks (10), размеры framebuffer (11/12). Память фиксирована 2 MiB. Проверки используют тот же WASM, что и игра; тестовой телепортации нет.

## Запуск и сборка

Готовый WASM включён в репозиторий: для запуска нужен только `npm run dev`, затем `/rpg.html`. Ссылку на 2D-прототип можно найти в README; старый игровой интерфейс не менялся.

Для изменения C++ используйте существующий Emscripten SDK. Пример PowerShell для этой машины:

```powershell
$env:EMSDK='C:\Users\serik\Desktop\тарих\tools\emsdk'
$env:PYTHON=Join-Path $env:EMSDK 'python\3.13.3_64bit\python.exe'
npm run engine:rpg
npm test
npm run build
```

Скрипт использует `EMCC` и `PYTHON`, если они заданы. Без `PYTHON` Windows использует Python 3.13.3 из текущего SDK; на других SDK задайте путь явно. Зависимости не устанавливаются. После изменений C++ пересобирайте WASM до тестирования/релиза; `npm run build` упаковывает уже собранные движки, как в Beta.

Браузерная проверка: запустите Vite/preview, затем `npm run check:rpg -- http://127.0.0.1:5173`. По умолчанию используется установленный Chrome/Edge; можно задать `BROWSER_EXE`. Скриншоты сохраняются в игнорируемый `test-results/`.

## Совместимая архитектура продолжения

Не перенумеровывать текущие десять уровней в восемь: существующие попытки ссылаются на старые номера и ключи. Следующая серверная миграция должна вводить идентификатор/версию кампании и восемь новых эпох в **той же Supabase БД**, сохраняя legacy-вопросы/попытки. До этого 2D прототип не публикует результаты в рейтинг Beta.

1. Общие auth, profiles, sessions, members, QR и принципы RPC остаются. Версия кампании выбирается при создании сессии. Снимок опубликованного контента фиксируется для начатой попытки, чтобы редактирование ответов преподавателем не меняло уже оцениваемый квиз.
2. C++ хранит движение, столкновения, бой, взаимодействия и состояние сцены. Шлюз JS запрашивает тексты/варианты по стабильным ID задач, показывает UI и передаёт движку подтверждённые события. Ключи правильных ответов остаются приватными; финальный счёт принимает только сервер. Изменение опубликованного вопроса доступно новым попыткам через API без пересборки WASM.
3. Будущая `/admin/` — отдельный вход Vite, общий auth-клиент, отдельные API и интерфейс. Dashboard, Players, Teams, Sessions, Levels, Quizzes, Tasks, Analytics внедряются последовательно с работающими операциями.
4. Роли проверяются сервером: Player — собственные попытки/разрешённая сессия; Teacher — учебный контент, свои сессии/команды и их результаты; Administrator — все сессии, пользователи/роли, публикация и аудит. Самостоятельное назначение роли через клиент запрещено. Старый teacher registry требует явной миграции в новую модель прав.
5. Каждая привилегированная мутация: проверка прав и полей, UUID запроса + проверка совпадения тела, транзакция, приватный audit log (актор, действие, объект, время, изменение). Права выдаются только оператором БД/защищённой admin-функцией; service-role ключ не попадает в Vite. Итоговые баллы нельзя редактировать из CRUD.
6. Тесты будущей панели: Player/anon отклонены на уровне API, Teacher ограничен областью доступа, CRUD и повтор запросов, защищённые ключи, статистика реальных данных, обновление контента без изменения хэша WASM.
