# Безопасность Tarikh Joly

Проверяйте изменения вместе с разработкой: воспроизведение → исправление → регрессионный тест → сборка. Сначала CRITICAL/HIGH. Не тестировать чужие аккаунты и production.

Секреты хранятся только на сервере. VITE_* доступны каждому посетителю; разрешены лишь URL и publishable key Supabase. Service-role, OAuth secret и пароли в браузере/WASM запрещены. При утечке отозвать ключ, заменить его и проверить историю Git; удаление из текущего файла недостаточно.

Права проверяются SQL RPC и RLS, а не UI. Применять все миграции последовательно. Локальные результаты и сохранения недоверенные: они не подтверждают достижения для рейтинга. Клиентские ключи офлайн-квизов доступны для изучения.

/admin.html — демонстрация на искусственных данных, без подключения CRUD к серверу. Переключатель ролей показывает интерфейс и не выдаёт права. Не вводить реальные персональные данные. Классные сессии рейтинга отличаются от кооператива персонажей. Реализованный клиентский кооператив BroadcastChannel/Realtime не является доверенным серверным режимом: см. HIGH в KNOWN_ISSUES.md.

В продакшене нужны HTTPS, разрешённые OAuth redirect URLs, корректные MIME для JS/WASM и проверенная политика CSP/CORS на хостинге. Не добавлять permissive CORS к приватным API. CSP нужно проверять с WASM и текущими inline-обработчиками, прежде чем включать enforcement.

Сообщение об уязвимости: версия/commit, затронутый компонент, минимальный локальный пример, ожидаемый и фактический результат. Не публиковать токены, сохранения с персональными данными или рабочий exploit против внешнего сервиса. Передавать детали владельцу проекта закрытым каналом.

Границы проверки и оставшиеся риски: SECURITY_AUDIT.md и KNOWN_ISSUES.md.
